# 设计稿：化学药剂与 mol 计量体系

> 写于 2026-10-14。下一特色工业体系的设计基线。
> 本稿**只定方向与判据**，不含实现；锚点数值凡未定者显式标注「待定」。

---

## 〇、这张稿子要解决的病

化学药剂（盐酸这类）**按体积 mB 记账很麻烦**，因为同一物质可能以两种相态出现：

- **气体**：HCl 常温就是气体，"1 mB 氯化氢气体"随 T、P 变；
- **溶液**：盐酸 = HCl 溶质 + 水溶剂，"1 mB 盐酸"里有多少 HCl 取决于浓度。

于是**同一个物质、两个相态、外加一个不参与反应的溶剂**，三条线全挤在"体积"这一个数上 —— 体积口径必然分裂。

**mol 修的就是这个**：mol 是"有多少个分子"，与相态无关。1 mol HCl 无论是气态还是溶于水的，都是同一件事。

---

## 一、核心命题：mol 是内容单位，质量是第二本征量；B 只是显示名

> **2026-10-14 修订**：原稿把 `mB / B` 当第三种记账量（"由 mol 推出"）。现**砍掉 B 系统** —— B 退为**纯显示名**，所有机器与物品只认 **mol 与质量**。

| 概念 | 地位 | 随什么变 |
|---|---|---|
| **内容**（药剂本体） | **mol**（唯一本征记账量） | 不随相态、温度、浓度变 |
| **质量** | **g** = Σ nᵢ·Mᵢ（派生，精确） | 由 mol 与 M 精确决定，**相态无关** |
| ~~**体积 / B**~~ | **纯显示名**，不进账 | 仅"给人看的人话"，不参与任何守恒/配平/判定 |

**为什么砍 B**：`质量 = n·M` 是**精确恒等式且与相态无关**（不像体积）；所以 **mol + g 是一对自洽本征量**，而体积那个"随相态/温度/浓度分裂"的病根（§〇）**被连根拔掉**。

一句话：**载体恒定，内容由组件承载** —— 与主模组 `geometallurgy:ingot` + `ingot_composition` 组件同构。

### 1.1 锚点

| 常量 | 值 | 状态 |
|---|---|---|
| **1 mol ≡ 1 B = 1000 mB** | **1 : 1** | **已定（2026-10-14）** —— B 是**固定比例显示名**，不查物性 |
| 一桶容量 **N = 15 mol** | = 15 B | **已定（2026-10-14）** |
| 摩尔质量 M（每物质一个常数） | 数据包定义 | 待定（推质量 g 用） |
| ~~气体标准态 Vₘ~~ | — | **已不需要**（B 不再反映真实体积） |

**锚点已定**：**1 mol = 1 B**（"好理解"、且 mol 与 B 一比一）。于是 B 的显示**不随相态变、不需要密度**。

## 二、载体：三形态

| 形态 | 说明 | 类比 |
|---|---|---|
| **金属桶**（新物品） | 固定盛放 **N mol**。一个物品 id + 一个「药剂成分组件」（药剂 id → mol 数）。桶上若标"30 B"只是**口语显示名**，不承载任何换算语义 | 统一锭 + `ingot_composition` |
| **保留内容的方块** | 挖掘时**保留内部容器**，不撒内容物 —— 罐子被挖掉，带着它的 mol 内容一起掉 | 现有 BE 的 `saveAdditional` / `dropContents` |
| **机器兼容槽位** | 见 §四 | 现有 `Reagent` 槽 |

三者都指向同一个「药剂成分组件」。

## 三、mol 的两个派生量：质量（精确）与 B（固定显示）

记账只有 **mol**；质量与 B 都是它的派生。

| 派生量 | 公式 | 性质 |
|---|---|---|
| **质量 g** | m = Σ nᵢ·Mᵢ | **精确**、相态无关，由 mol 与 M 决定 |
| **B（显示名）** | **B = n**（1 mol ≡ 1 B = 1000 mB） | **固定 1:1**，不查物性、不随相态 / 温度 / 浓度变 |

**要点**：

- **B 的 1:1 是纯约定**（"好理解"），**不带物理含义** —— 所以**不需要密度 ρ、不需要气体标准态 T/P、不需要溶解度判定**。
- 真实物理体积（nRT/P、n·M/ρ）本稿**一律不再使用**；若将来某处确实要"真实体积"，单独开一层，不污染记账。
- 盐酸的账 = `{HCl: n₁ mol, H₂O: n₂ mol}`，两组分**分开存**，溶剂体积不再影响任何计算。

**配套原则：显示可为混合物（有损），成分必须分离（无损）。** UI 可以把同分异构体聚成一个"馏分"显示，但**账本必须按成分分开存 mol**（见 §十）。

> 唯一残留的待定：**桶容量 N**（建议 15 mol）。

## 四、机器分两类：泛用机 vs 专用机

| 机器类型 | 对 mol 输入的态度 | 显示 |
|---|---|---|
| **泛用机器** | **兼容** mol 物品 —— 药剂槽接受 mol 载体 | 同时给出 **mol 与质量 g 两个总量**，按机器性质**取一个作主容量**；B 仅作可选的口语显示 |
| **专用机器**（如粉碎机） | **直接拒绝** mol 类型输入 | — |

- **主容量由机器性质定**：例：离心机 / 按密度分层 → 主容量看**质量**；按化学计量的机器 → 主容量看 **mol**。哪台看哪个，在机器侧声明。
- **拒绝是硬的**：专用机器（粉碎机）不接受 mol 载体，不做"折合"。

> 待定：每台机器的主容量口径（列一张 机器 → 主容量单位 的表）。

## 七、为什么值得做（与主线的关系）

主模组的特色是**成分驱动**。现有 `Reagent.units()` 已经是"脱离体积的抽象当量"，但它**不本征** —— 碳粉 1.0、煤炭 0.8 是拟合出来的数。mol 化把它拉回本征：

- **配平回到整数**：Fe₂O₃ + 6 HCl → 2 FeCl₃ + 3 H₂O，药剂用量按系数配。
- **气液统一**：气体与溶液共用一套 mol 接口，这正是"气体+液体"要并列的原因。
- **同构复用**：桶 = 药剂的统一锭，"载体恒定、内容在组件"——与主模组的核心模式一脉相承。

**mol 不是给 mB 打补丁，是给"成分驱动"补上计量层的那块。**

### 8.2 已识别的方向错误（**勿照旧稿实现**）

**① mB ↔ mol 的桥搭反了。**

旧蓝图的桥：`1 mB × ρ = 质量；质量 / M = mol` —— **mol 由体积推出**。它的全部例子（水、乙醇、铁）都是**凝聚相**，默认了"体积第一性"。

但 §〇 已论证：对**气体与溶液**，体积第一性必然分裂。**正确方向是本稿 §一/§三：mol 第一性，体积由 mol + 相态推出。**

> 本设计稿与旧蓝图在这一点上**不能同时成立**。以本稿为准。掉转方向后，§8.1 的分层架构照样成立、且更干净 —— 气体从"例外"升级为"一等公民"。

**② 「只存官能团、不存结构」—— 取决于它是「列表」还是「树」。（2026-10-14 修订）**

原判批评得**偏了**。按用户的更正：

- 若指**无序列表**（`{ -OH, -CH₃ }`）：确实过强，丙醇 / 异丙醇撞墙。
- 若指**有根有序树**：**成立**。树拓扑本身就编码结构 —— **子节点的左 / 右（有序）就是手性中心**：交换两个子节点 = 对映体。旧稿补的 `branching`、`ring_count` **不是"结构偷偷长回来"，而是从「列表」升级为「树」的正确一步**。

**我此前说的"需结构指纹"，与"树"并不冲突** —— **树的正则形式（canonical form）就是那个指纹**。分歧只在"列表 vs 树"，不在"要不要结构"。旧稿此处没错，只是**没把"列表→树"这一步说清**。

**成立的条件（是适用范围，不是反驳）**：

1. 树必须**有根、有序、固定子序** —— 左右不可互换；一旦允许自由"旋转"（子序等价），**手性立刻丢失**。即**树的不对称性就是手性信息的载体**。
2. 手性中心常有 3–4 个不同取代基 → 需**有序 n 叉**（二叉树只是链式骨架的特例，不足以覆盖一般立体中心）。
3. **环无法用纯树表达** —— 需扩成图（树 + 环闭合）。旧稿已意识到（无根树 → 带环）。
4. **身份判定需正则化**：同一分子有多种树编码，必须有 canonicalization，否则同一物被当成两物。

> 术语澄清：「旋转异构」若指**构象异构（conformer）**，那是**动态层**，静态树表达不了 —— 但那是另一个层次的问题，与"身份判定"无关；此处按**树的子序不可旋转**理解。

### 8.3 复杂度螺旋警告（实施纪律）

旧对话里几乎每一步都被评"优雅/精妙"，从 无根树 → 带环 → 高分子 → 积分 → δ函数 一路升级，直到用户自己反问"我们真的需要这个吗"。

**判据**：游戏能吃到的是前 ~20%（分层查询 + 三粒度）；后 ~80%（积分、样条、窗口函数、δ函数）是数学自洽的自我满足，**未必有玩家看得见的收益**。

**具体纪律**：

- **「通用工艺单元方块 / 蓝图刷机」暂缓**。现有 `SmelterBlockEntity`（一个 BE + `SmelterProfile` 表 = 三台炉）**已经是该思想的正确尺度**（3 个 profile，不是 50 个）。等真有三五类新设备时再抽通用壳；现在抽是空转。
- **新构想进入实现前，先问一句**：玩家能看见它带来什么？答不上来的一律延后。

## 九、同类做法调研（2026-10-14）

> 目标：看别人怎么把"化工"塞进 MC，以校准本稿的定位。

### 9.1 两大流派

| 流派 | 代表 | 计量口径 | 成分表达 |
|---|---|---|---|
| **元素/分子派（离散）** | MineChem、Alchemistry + **ChemLib**、GregTech(CEu) | **1 个物品 = 1 个单元**（vial / 桶 / cell）；**没有"数量"** | 物质定义直接挂**化学式 + 配平系数** |
| **流体派（连续）** | **Mekanism**、Create、IC2 | **mB**（气也用 mB） | Create 无成分；Mekanism 靠 substances + attributes 表 |

### 9.2 逐家要点

**① ChemLib / Alchemistry —— 最接近本稿的一支。**

- ChemLib：118 元素 + 数十化合物，**物品态 + 流体态双形态**；"**倒置桶 = 气体，正桶 = 液体**"。
- **化合物数据结构**（`compounds.json`）：
  ```json
  { "id":"chemlib:water", "abbreviation":"H2O",
    "ingredients":["chemlib:hydrogen","chemlib:oxygen"],
    "ingredient_counts":[2,1], "matter_state":"liquid" }
  ```
  → **`ingredients` + `ingredient_counts` 就是化学式与配平整数比**。**这正是本稿 §五 想把 `Metallurgy.stoichiometry` 本征化成的形状**，可直接抄数据结构。
- 缺陷（正是本稿要补的）：它**离散到"一个 vial = 一个分子"**，没有物质的量。要 2 个水分子就摆 2 个 vial —— 没有"1 mol = 6.02e23 个"这一层。**mol 是它缺的那一格。**

**② Mekanism —— 纯 mB 派，且证明"化学可作第二条通道"。**

- 四类化学：**Gas / Infuse Type / Pigment / Slurry**，独立于流体体系（**Pressurized Tube ≠ Fluid Pipe**）。
- 全部按 **mB** 计量（1920 mB/t 燃烧率、100 mB H₂…）。**气体也是 mB** —— 正是本稿 §〇 要避开的"气体按体积算"，但它**照样被玩家接受**。
- 物质带 **attributes 表**（radioactivity / coolant / fuel）—— 与本稿 `SlurryProps` 同类，是扩展物质的现成范式。
- **Mekanism: Elements** 加 25+ 化学品（硝酸、氨、王水…），每个带 temperature/density/color —— **density 正是本稿 §五 要补的 M 的邻居**。

**③ GregTech (CEu) —— 材料定义内嵌化学式。**

- 材料注册：`.components("1x gold","1x lead","1x silver")` / `.element(GTElements.C)` / `.formula("C₃O")`。
- **物质本身带化学式 + 计量系数（1x）**；配方以现实化工为蓝本。
- 计量仍走 **mB + Cell**。**贡献**：`components` 的"化学式挂材料 + 系数"与本稿 §七"配平回到整数"完全同向。

**④ Create —— 流体派极端，无成分。**

- Basin 每格最多 **1000 mB** 流体 + 最多 16 个物品；机械搅拌出配方。
- **完全不碰成分** —— 反衬本模组"成分驱动"的位置。可借鉴的是**交互形态**（Basin 可直接由玩家/管道双向进出流体）。

### 9.3 调研结论（对本稿的四条校准）

1. **"mol vs mB"不是成败关键**。Mekanism 用 mB 也做出了被广泛接受的化工。mol 的真收益是**配平（整数系数）**与**气相守恒**，不是"更真实"——这条要写进理由栏，别把"更真实"当卖点。
2. **本稿占的是一个没人占的位置**：**连续的物质量（mol），且与体积解耦**。离散派（vial）无数量；流体派（mB）无本征成分。**mol 卡在两者中间**——这正是特色所在。
3. **数据结构可直接抄 ChemLib**：`ingredients + ingredient_counts`（配方按元素/化合物 + 整数系数表达）比现在 `stoichiometry` 的经验系数（1.00/0.40/1.20）本征得多。
4. **"化学是独立于流体的第二条通道"有先例背书**：Mekanism 的 tube/pipe 分家证明玩家接受"药剂走专门通道"。本稿 §四"泛用机兼容、专用机硬拒、mol 是并列的一套账"由此不显突兀。
5. **可借的现成范式**：Alchemistry 倒置桶（§二 桶形态 UI）、Mekanism attributes（§五 SlurryProps 扩展）、GT `.formula()`（物质挂化学式）。

### 9.4 补充观察：科技派 vs 化学派至今没合流（用户 2026-10-14 提出）

| | **化学模组** | **科技模组** |
|---|---|---|
| 优化对象 | **物质本体**（它*是什么*：元素 / 分子 / 化学式） | **过程**（*怎么造*：机器 / 能量 / 吞吐） |
| 计量 | 离散单元（vial / 桶），**无"数量"** | mB / FE / 槽位，标度随意 |
| 成分 | 是核心（formula、ingredients） | 基本不管（物质只是一个名字） |
| 代表 | MineChem、Alchemistry、ChemLib | Mekanism、Create、GregTech、IC2 |
| 缺什么 | 没有工业尺度（流速 / 能耗 / 产线 / 自动化） | 不在乎物质**本体** |

**观察**：两派**平行发展、几乎不交叉**。最接近的 Mekanism 也只到"给气体起名 + 当 mB 流体"，**从未采用物质身份或化学计量**；GT 把化学式挂进材料定义，但计量仍是 mB + 槽位。

**本模组的位置**：**科技派的骨架 + 化学派的本体** —— 有机器 / FE / 配方 / 矿处理的工业形式（科技派），却以**成分（composition）**为本体、以 **mol** 为计量（化学派）。这正是「成分驱动」落在两派夹缝里的地方。

**所以 §9.3 结论 2 可再推一步**：不是没人做"物质的量"，而是**没人把「化学本体」装进「工业机器」里**。这才是本模组真正空着的位置。

## 十、有机物表示与哈希识别（2026-10-14 决定）

**问题**：有机分子的结构是树 / 图（§八），若每次判定都遍历树，太贵。**判定不该发生在"比较身份"时，只该发生在"化学反应"时。**

### 10.1 三层分工

| 层 | 表示 | 何时用 |
|---|---|---|
| **存储 / 身份** | **唯一哈希码**（canonical hash） | 一切比较、槽位、组件、网络传输（O(1)） |
| **结构定义** | 树 / 图（原始定义） | 数据包静态资源；生成哈希的**源** |
| **特性分析** | 官能团集合 / 反应性 | **只在化学反应发生时**展开一次 |

**核心**：哈希 = 身份（快）；树 / 图 = 离线的源；特性 = **惰性求值**，只在反应时算。

**配套原则：显示可为混合物（有损），成分必须分离（无损）。** UI 可以把同分异构体聚成一个"馏分"显示，但**账本必须按成分分开存 mol** —— 与 §一 / §三 的"显示 / 记账分离"同一条原则。

### 10.2 与 §八.2② 的关系

§八.2② 说"身份判定需 canonicalization" —— **本节的哈希就是那一层**：**canonical form 生成一次 → 哈希 → 之后全走哈希**。不必每次判官能团。

### 10.3 分子集合：混合策略（2026-10-14 定）

**已知化合物离线预生成；未知化合物运行时即时哈希，并写入存档。**

| 层 | 来源 | 生命周期 | 成本 |
|---|---|---|---|
| **1. 数据包**（已知） | 随 mod / 数据包发布 | 只读、**跨存档** | 零（预计算） |
| **2. 存档缓存**（曾生成的未知） | 写进 save | **per-save** | 零（查表） |
| **3. 即时生成**（首次遇到） | 运行时 canonicalize + 哈希 | 生成后**写回第 2 层** | 一次性 |

**查找顺序 1 → 2 → 3，命中即止**；第 3 层生成后**持久化**到存档。**本质是一次 memoization** —— 昂贵计算只做一次，结果进存档，之后全走查表。

它同时满足两个方向：**离线可预计算的走快路（1、2），开放生成的只付一次钱（3）**。

### 10.4 两个前提约束（早先已定）

1. **canonical form 必须"保留异构、只归并写法"**（2026-10-14）：
   - **要归并**：**同一分子**的不同树编码（子序不同、多个等价根）→ 同一哈希。
   - **不能归并**：**同分异构体 / 对映体必须不同哈希** —— n-丁烷 ≠ 异丁烷，左旋 ≠ 右旋。化学性质本就不同，合并即错。
   - → canonicalization **必须立体 / 位置敏感**（§八.2② 的"有序固定子序"**不能省**）：**把子序归一 = 错并对映体 = bug**。
2. **哈希是单向的** —— 反推不出官能团，故必须**另存结构定义**（第 1、2 层都带树 / 图），特性在反应时按需展开。

### 10.5 混合策略的四个硬约束

1. **确定性**：canonical form 与哈希必须**平台无关、与遍历顺序无关**。同结构 → 同哈希，跨机器、跨存档一致；否则存档不可移植。
2. **服务端权威**：生成与写入**只在服务端**做（单一权威），客户端只读哈希。否则多人 / 客户端各自算会分叉。
3. **两表一致性**：**存档缓存从属于数据包**。若某分子后来被加入数据包（未知 → 已知），**数据包优先**，存档缓存须被校验 / 覆盖 —— 否则同一哈希挂两条定义。
4. **增长上限**：未知分子无限生成会让存档膨胀。需要**上限 / 回收策略**（尤其玩家能自由造分子时）。

### 10.6 版本迁移

改 canonical 算法、或加新已知化合物，都需要**分子格式版本号**。版本一变，存档里的旧缓存要么**迁移**，否则**失效重算**。这条务必写死，早晚会踩。

### 11.5 反应釜（新增机器规格）

**纯容器型**，不是带炉膛的冶炼机。规格：

| 槽 | 数量 | 说明 |
|---|---|---|
| **流体输入槽** | **2** | 两个不同流体的 mol 输入（如 NaCl 溶液 + H₂O，或 Cl₂ + H₂） |
| **催化剂槽** | **1（可不放）** | 只做"有没有催化剂"判定，不消耗（催化 = 放宽条件 / 降耗），非原料 |
| **流体输出槽** | **1** | 混合反应产物，mol 输出 |

- **反应在容器内按 mol 配平**：输入组分按整数系数化合成输出，多余组分留下（不强制耗光）。
- **催化剂是可选项**：放与不放改变反应条件（速率/收率/是否发生），本身不进入产物、不消耗。
- **主容量 = mol**（化学计量的机器看 mol，符合 §11.1 口径）。

> 注意：此处"催化剂槽"与现有 `Reagent` 的"辅助剂槽"语义不同 —— `Reagent` 是**消耗性原料**（碳/电极/活泼金属），催化剂是**非消耗条件**。两者都挂 mol/当量，但角色不同，实现时别混。

> **实现状态（2026-10-15，已被 §12 取代）**：下面的「4 槽」方案是**第一版**，已按用户口径改成版本 B（机器内部一本混合 mol 账、界面无桶槽、桶走相邻容器）；留作历史记录。原记录：反应釜方块 + BE 已落地。`reaction_vessel` 方块（LIT 属性，仿 CrusherBlock）+ `ReactionVesselBlockEntity`（4 槽：2 输入桶 + 1 催化剂 + 1 输出桶，每 tick 合并两输入桶账、逐条查 `MolRecipes` 配平、按整数系数生成产物灌输出桶）。催化剂走语义 id 映射（`light`→碳棒、`vanadium_pentoxide`→钼棒），只判存在不消耗。配套 `ReactionVesselMenu` / `ReactionVesselScreen`、`MetalBucket` 化学桶（`bucket_stock` 组件）+ 语言键 + 资源模型均已注册，`./gradlew build` 通过。待办：六面搬运的相邻容器抽取/推送（目前由漏斗/玩家手动进出）、电解炉改造收 mol、置换炉改造收 mol。

### 11.4 一个依赖关系（定首批顺序）

轨 B 的溶液**依赖**轨 A 的气体/单质（盐酸靠 Cl₂+H₂，硫酸靠 S+O₂）。所以**首批实现顺序**：先轨 A（简单气体/单质）→ 再生成立氯化/制酸 → 轨 B 溶液才有原料。**轨 A 是地基。**

## 十二、实现记录（版本 B，2026-10-15 定稿）

§11.5 的「2 输入桶 + 1 催化剂 + 1 输出桶」四槽方案作废。用户口径（原话）：
「搅拌器只有一个混合 mol 槽，然后可以配置输出液体、气体或者固体，反应釜也是这样……
搅拌器可以直接控制两个流体输入槽混合到流体输出槽的比率」，以及
「直接用容器桶放在一个面上，然后配置输出不就行了？」

### 12.1 机器内部模型

- **一本混合 mol 账**（`MolStock`），容量 `TANK_CAPACITY = 90 mol`。不是流体槽，也不分相 —— 相只在**输出时**按 `Chemical.Phase` 筛。
- **搅拌器额外两个配比缓冲**（A / B，各 90 mol）：先按 `ratio`（默认 50%，5% 一档）把两路料并进主账，再在该组成上匹配反应。
- **催化剂槽是界面里唯一的槽**，只判存在、不消耗。语义 id → 物品：`light` → 碳棒，`vanadium_pentoxide` → 钼棒。不为新反应加催化剂 id，省掉物品注册。
- **反应速率** `RATE_PER_TICK = 1.0 mol/tick`，逐条查 `MolRecipes`，按限制试剂推进；账上残留是正常的。

### 12.2 桶的进出（无桶槽）

- 六个面各有一个角色：反应釜用 `PortRole`（disabled / input / output / byproduct），搅拌器必须另立 `MixerRole`（disabled / input_a / input_b / output），因为四值已被占用。
- 放置时**六面全 disabled**，必须用工程配置器打开。
- **输入面**：`level.getBlockEntity(pos.relative(side)) instanceof Container` → 找到装了东西的 `metal_bucket` → 内容并入账 → 空桶推回原容器。账只扣**实际被接受的量**。
- **输出面**：按选定的相取产物装满空桶 → 推进相邻容器；**每刻最多一桶**。
- 选相按钮在界面上循环 液 / 气 / 沉淀；搅拌器另有三个按钮调比率（−5% / +5% / 复位 50%）。

### 12.3 同步与持久化

- `ContainerData` 十格：账量、质量、状态、输出相、六面角色打包、比率、缓冲 A、缓冲 B、主成分下标、主成分 mol。16 位有符号上限 32767，所以账量 / 缓冲 / mol 全部 **×100**。
- 主成分只存下标 → **`Chemical` 表里原 15 种物质的顺序是协议的一部分，不能重排**。
- NBT：`roles` / `phase` / `ratio` / `tank` / `items`；搅拌器的两个缓冲单独存取。`MolStock.moles` 是 final，反序列化走 `clear()` + `add()`。

### 12.4 稀土链与药剂来源

稀土分离不需要第三个方块，全靠反应釜 / 搅拌器：

```
RE2O3 + 6 HCl        → 2 RECl3 + 3 H2O            （反应釜即可）
2 RECl3              → LCl3 + HCl3                （需搅拌 → 搅拌器独占）
2 LCl3 + 3 H2C2O4    → L2(C2O4)3 + 6 HCl
2 HCl3 + 3 H2C2O4    → H2(C2O4)3 + 6 HCl
L2(C2O4)3            → L2O3 + 3 CO2 + 3 CO
H2(C2O4)3            → H2O3 + 3 CO2 + 3 CO
```

**遗留问题**：`RE2O3`（稀土氧化物）目前没有矿浆侧的来源，创造物品栏给了满桶药剂作为起步；接线到选矿 / 焙烧工序是下一阶段的事。

## 十三、桶的材质与耐蚀（2026-10-15）

用户提议：「给桶也加材质，因为部分化学药剂会侵蚀容器」。落地为**四种材质 + 一张侵蚀标签表**。

### 13.1 侵蚀标签

物质带一组标签（酸 / 氟化物 / 氧化剂 / 碱），材质声明自己**耐**哪些标签；

与 `Chemical` 的物质表分开维护（化学表只记「这物质是什么」，容器耐蚀性属于物品侧知识）。
类初始化时会逐个校验 id 存在，写错直接炸。

| 材质 | 耐 | 装得住什么（举例） | 配方 |
|---|---|---|---|

| **玻璃** `glass_bucket` | 酸、氧化剂 | 盐酸、硫酸、硝酸、氯水、高锰酸钾、氯化铁、稀土氯化物 | 4 玻璃 |
| **铅** `lead_bucket` | 酸、氟化物 | 氢氟酸、氟化钠、四氟化硅 | 4 金属锭 |
| **陶瓷** `ceramic_bucket` | 四类全耐 | 一切，尤其是所有碱（NaOH/KOH/氨水…）与氟气 | 4 黏土 + 4 砖 |

分配结果：铁 22 种、玻璃 19 种、铅 3 种、陶瓷 12 种。`BucketMaterial.cheapestFor(id)`
按声明顺序挑最便宜又耐得住的材质，创造物品栏的满桶药剂就是这么发的。

### 13.2 机器侧的行为（不「吃掉」玩家的桶）

机器**不会**把装不住内容的桶吸进来，也**不会**拿会被产物侵蚀的空桶去接料 ——
宁可停在那里报状态，也不破坏物品：

- 载具接口加了一条默认方法 `MolCarrier#holds(MolStock)`（默认恒真），
  桶用材质实现它。机器只问接口，不认识 `MetalBucket` —— 与「按接口 + 单位标签路由」一致。
- 吸桶时材质不符 → 跳过并置 `sawUnsafeBucket`；灌桶前材质不符 → 跳过并置 `pushBlockedByBucket`。
- 新增状态 `ReactorStatus.BUCKET_UNSAFE`（排在枚举末尾，不动既有序号），
  界面显示「桶不耐蚀：换一只耐蚀的桶放进去」。
- 输出排在反应之后，所以输出侧的标记由下一 tick 的 `react()` 读，差一 tick。

每个材质一套：`items/<id>_bucket.json`（`has_component` 条件 + `custom_model_data` 染色）、
`models/item/<id>_bucket.json`（空桶）、`models/item/<id>_bucket_filled.json`（流体层 + 该材质的镂空壳）、
`textures/item/<id>_bucket.png` 与 `<id>_bucket_hollow.png`（由铁桶贴图按材质主色重算亮度生成，

## 十四、储罐方块（2026-10-15 定稿）

用户口径：「我要的桶是实体方块啊，类似于沉浸工程的金属桶」。所以容器分两层：

| 层 | 是什么 | 容量 | 搬运方式 |
|---|---|---|---|
| **物品桶** `metal_bucket` 等 4 种 | 便携载体 | 15 mol | 拿在手上、机器从相邻容器的桶里倒 |
| **储罐方块** `*_barrel` 4 种 | 实体容器 | **60 mol（4 桶）** | 右键灌/倒；机器按面直接过户 |

**`MolTank` 接口**是两层之间的接缝：储罐实现它，机器只认它：

```java
MolStock tank();  double capacity();  default double room();
MolStock pour(MolStock amount, double maxMol);   // 收，返回实际收下的账
MolStock drain(double maxMol, Chemical.Phase phase); // 抽，null = 不分相
default boolean holds(MolStock stock);           // 材质耐蚀
static MolTank neighbor(Level level, BlockPos pos, Direction side);
```

反应釜 / 搅拌器在 `pullFaces` / `pushFaces` 里**先问邻面是不是储罐**：是就直接过户 mol，
不是才退回物品桶那条路。这一条同时满足两个要求 —— 「桶要能放外面」与「机器不必经过物品也能连容器」。

耐蚀规则对两层是同一套（`BucketMaterial`）：罐子只收它耐得住的料，机器也只往耐得住产物的罐里出料。

## 十五、金属锭锚点：1 锭 = 0.1 mol（2026-10-16 定）

用户口径：**一锭 = 0.1 mol**；其他一律不动（`BUCKET_MOL = 15` 保持原样，出矿量与反应数值零改动）。

| 载体 | mol | 说明 |
|---|---|---|
| **1 锭 / 1 件金属粉** | **0.1 mol** | `MolStock.INGOT_MOL = PowderContent.MOL_PER_POWDER = 0.1`；粉碎机 1 锭 → 1 粉是无损换算 |
| **1 桶**（4 种材质药剂桶） | **15 mol** | 不变；桶是**抽象的大量级**载体 |
| **1 mol** | **≡ 1 B = 1000 mB** | 不变（§一 锚点） |

**这个不对称是刻意的**：`15 / 0.1 = 150`，但 **1 桶 ≠ 150 锭**。桶与锭不是同一量纲下的东西 ——
桶是化工流程里「一大罐料」的搬运单位，锭是化学计量意义上的单质载体。拿「桶能装几锭」去推配平是错的。

**有意接受的抽象**：0.1 mol 的金属折成质量远小于现实里一块锭（Fe 0.1 mol ≈ 5.61 g，不是 837.8 g；
Cu ≈ 6.36 g / Zn ≈ 6.54 g）。MC 的单位本来就抽象，这里只把「锭 / 粉」这个锚点钉死在 0.1 mol 上，
好处是矿 → 金属的产量经济（出矿量、反应系数）完全不必重调。质量 `g = Σ nᵢ·Mᵢ` 仍是精确派生量，
只是它不再声称等于真实锭重。

实现落点：
- `chemical/MolStock.INGOT_MOL = 0.1`（`BUCKET_MOL = 15.0` 不动）；
- `metal/PowderContent.MOL_PER_POWDER = MolStock.INGOT_MOL`；
- 所有「一桶之量」的硬编码 15 改为**读载具自己的容量**（`MolCarrier.capacityMol()`）：
  `BarrelBlock.drainInto` 的抽取上限、`AbstractReactorBlockEntity.pushBucket` 的灌装上上限。
