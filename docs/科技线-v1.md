# 科技线 v1（2026-10-15 定稿草案）

> 用途：① 实现顺序的依据；② 任务书里那张**全屏全科技线网状图**的数据源。
> 每条边写清「谁产出什么、哪台机器、是否已存在」。

## 一、总图（节点 / 边）

```
[矿脉抽取机] ──固体矿石──┐
[流体抽取机] ──混合矿浆──┤
                         ├─→ [粉碎机] → 矿粉 ─→ [磁选机] ─→ 精矿 / 尾矿
                         │                      └→ [离心机] → 重相 / 轻相
                         └─→ 精矿 ─┬─→ [还原炉] ─→ 海绵金属（碳热）
                                   ├─→ [电解炉] ─→ 金属（熔盐：铝/镁）
                                   └─→ [置换炉] ─→ 金属（湿法）
精矿 ──(新增)焙烧档：还原炉──→ RE2O3（稀土氧化物）
水（新增：手持桶右键水源） ──→ 溶剂
NaCl 溶液 ──(新增)电解炉·溶液电解档──→ NaOH + H2 + Cl2      （氯碱）
H2 + Cl2 ──(需搅拌)反应釜/搅拌器──→ HCl（盐酸）
自然硫 S ──(新增)焙烧档：还原炉──→ SO2 ─→[反应釜,搅拌] SO3 ─→ H2SO4（硫酸）
NH3（N2+3H2 搅拌） + HCl → NH4Cl；NH3 + H2O → NH4OH；HNO3 + NH4OH → NH4NO3
RE2O3 + 6HCl ─→ 2RECl3 + 3H2O            （反应釜）
2RECl3 ─→ LCl3 + HCl3                     （**必须搅拌** → 搅拌器：轻重稀土分家）
LCl3 + 草酸 → 轻稀土草酸盐 ；HCl3 + 草酸 → 重稀土草酸盐
草酸盐 ─焙烧→ L2O3 / H2O3（轻/重稀土氧化物）
```

## 二、三个「新增能力」（本版要做的）

### 1. 电解炉：溶液电解档（用户口径：酸碱试剂靠电解金属盐溶液）
- 现状：电解炉只吃**熔盐电解**（金属氧化物 → 金属）。反应表里已有 `2 NaCl + 2 H2O → 2 NaOH + H2 + Cl2`。
- 要做的：给电解炉加一条**溶液电解**通路——输入是 mol 账（桶/储罐送进来），在**耗电**的情况下驱动
  **标记为电解型**的反应（新增一个标记，区别于 `requiresStirring`）。
- 建议实现：`MolBalance.Reaction` 加一个枚举/布尔 `kind = THERMAL | ELECTROLYSIS | STIRRING`（或并列布尔 `requiresPower`），
  `Reactor.runAll` 多收一个「本机允许的反应类型集合」；电解炉传 `{ELECTROLYSIS}`，反应釜传 `{THERMAL}`，
  搅拌器传 `{THERMAL, STIRRING}`。这样三台机器共用一张反应表，不各写一套。
- 首批电解反应：氯碱 `2NaCl + 2H2O → 2NaOH + H2 + Cl2`；`2H2O → 2H2 + O2`（水电解，制氢氧）。

### 2. 手持桶右键水源（用户口径：水直接取自水源）
- `MetalBucket`（或统一的桶物品基类）实现「右键水方块 → 装 15 mol 水」：
  判定 `level.getFluidState(pos).isSource()` 且是水；装成 `MolStock.of("water", 15)`；
  桶里已有别的料就不抢；装完写回手牌（复用 barrel 那套 `handOffOne` + `inventoryMenu.broadcastChanges`）。
- 签名必须先 javap 核实（26.x 的 `Item.useOn` / `useOn(ItemStack, ItemUsageContext)` 之类），不要凭 1.21 经验写。

### 3. 任务书：全屏科技线网状图
- 现状：`manual/Manual.java` 是「章 → 条目 → 段落」的树，`client/ManualScreen` 一页页翻，`manual/ManualRecipes` 传配方网格。
- 要做的：新增一个**全屏网状图页**（从任务书里一个按钮进入）：
  - 节点 = 机器 / 药剂 / 中间产物，分列成「矿 → 选矿 → 冶炼 → 化学 → 稀土」几层；
  - 边 = 本文件第一节那些箭头，画贝塞尔或折线，箭头指向下游；
  - 交互：鼠标悬停高亮该节点的上下游 + 显示名字（用**已有的** `block.geometallurgy.*` / `chemical.geometallurgy.*` 键，别新增一堆 lang）；
    拖动平移、滚轮缩放（可选，先做平移+固定缩放）；
  - 数据：写死在 `manual/TechTree.java` 之类的一张表里（节点 id → 层/列/名字键；边 = (from,to)），
    界面只负责画——**不要**塞进数据包，避免和配方表耦合。
- 面板尺寸约定照旧：全屏图不套 222 的限制，但要自己处理窗口 resize。

## 三、实现顺序

1. 桶取水（最小、独立，先把"水"变成可得资源）。
2. 电解炉溶液电解档（打通酸碱自产：氯碱 → NaOH/Cl2/H2）。——需要动 `MolBalance/Reactor/电解炉/菜单/界面`，是本版最大的一块。
3. 焙烧档（还原炉）：RE 精矿 → RE2O3；自然硫 → SO2。让稀土链与硫酸链在生存里闭环。
4. 任务书全屏网状图 + 「科技线」章节文案。
5. 收尾：储罐界面、`MetalBucket.setStock` 容量钳制、香草式一摞桶拆分、搅拌器饼图分 A/B。

## 四、mol 账的相态标注 + 电解炉的阳极/阴极容器（2026-10-16 用户口径）

用户原话：「容器内部 mol 物品要标注状态，比如气液固必须分开形成混合物」；
「电解炉不应该有矿粉和渣槽位，应该有阳极容器（存放该电极产生的固体和气体，液体留在溶液中），和阴级容器（同理）」。

### 4.1 相态标注（显示层）
- 一切「容器内容」读数都要**按相态分组**，每组内部才是混合物：
  ```
  气体：H2 12.0 mol · O2 3.0 mol
  液体：H2O 5.0 mol · NaOH 2.0 mol
  固体：—
  ```
- 落地位置：`MetalBucket.appendHoverText`、`BarrelItem.appendHoverText`、电解炉溶液读数、以及各饼图。
- **现成工具**：`chemical/PhaseSplit`（`split()` 返回相 → 账，`spansMultiplePhases()`，目前**全仓库没人调用**）——直接用它，别再造一份。
- 饼图：每个相各占一块，`SlurryPie.Slice.children` 放该相内的物质（浮层里缩进列出）——这就是"气液固分开形成混合物"。
- 相名复用已有键：`gui.geometallurgy.phase_gas / phase_liquid / phase_solid`（固体那档现在写作"沉淀"，够用；要改成"固体"再单说）。

### 4.2 电解炉：阳极 / 阴极容器（数据层）
真实电解就是这样：**液体留在溶液里，气体和固体按电极分家**。
- `MolBalance.Product` 增加电极归属：`enum Side { NONE, ANODE, CATHODE }`，保留 2 参构造器（默认 `NONE`），33 条旧反应零改动。
  现有的两条电解反应标一下：`Cl2 → ANODE`、`O2 → ANODE`、`H2 → CATHODE`、`NaOH → NONE`（留在溶液）。
- 电解炉（`SmelterBlockEntity` 的溶液路径）从"一本溶液账"变成**三本账**：
  `solution`（液体 + 未分家的）、`anode`（该电极的气体与固体）、`cathode`（同理）。
  做法建议（最小侵入）：反应仍在 solution 上跑，跑完立刻把**该轮产物**里 `Side != NONE` 的成分从 solution 挪到对应电极账；
  `Side == NONE` 的留在 solution。三个账各自走邻面 `MolTank` 进/出，各自存档与同步（`ContainerData` 16 位，mol ×100 钳制）。
- **删掉矿粉槽与渣槽**（电解炉这条路上不该有）：`SmelterMenu` 里对 `usesSolution()` 的机器**不添加**那两个槽；
  腾出来的位置放**阳极容器 / 阴极容器**的液位条 + 成分页签（不是物品槽，是内部账）。
- 饼图页签扩成：溶液 / 阳极 / 阴极（现在只有 溶液）。
- 界面文案新增（由实现方负责）：`gui.geometallurgy.smelter_anode_vessel`、`...smelter_cathode_vessel`、
  `...smelter_pie_anode`、`...smelter_pie_cathode`（中英各一份，键集必须一致）。
- **后续修正：共用面角色的兜底已替换为专用枚举。** 阳极 / 阴极容器原先与溶液共用 `PortRole`，
  进料靠「把邻罐整罐抽干、留下要的、其余倒回」。这条兜底已废弃：电解路改用独立枚举
  `ElectrolysisRole`（`DISABLED / SOLUTION_IN / SOLUTION_OUT / ANODE_OUT / CATHODE_OUT`，5 值 3 bit，
  六面 18 bit 拆两个 `ContainerData` 槽同步，同反应釜 / 搅拌器）。三本账各走各的面：`SOLUTION_IN`
  从邻罐抽溶液，`SOLUTION_OUT` 只推非电极产物，`ANODE_OUT` / `CATHODE_OUT` 各推自己那一本；
  电极账不再从邻罐抽料（内容全部来自反应），「抽干再倒回」的写法已删除。还原 / 置换两路仍用
  `PortRole`（2 bit）不变，存档另有 `electro_roles` 键与旧档迁移。
- **后续修正：补回熔盐档的粉 / 渣面。** `ElectrolysisRole` 再增 `POWDER_IN` / `SLAG_OUT`（7 值仍 3 bit）：熔盐档吃矿粉、出渣，
  溶液档仍是溶液 / 阳极 / 阴极三本账；界面按「有没有配粉进 / 渣出面」在两套布局间切换（bug#18）。

## 六、反应表的超边图 + 启动可达性审计（2026-10-17）

这一步把「反应表」由一张平表升级成一张**超边图**，并加了一个便宜的启动期报告。协议、存档、
`ContainerData`、界面一律没动，反应表的配平与质量守恒校验也没动（`MolRecipes.add` 仍在类初始化时逐条查）。

### 6.1 模型
- **节点 = 物质**：`Chemical` 的 56 条物质，外加矿世界的原矿 / 精矿节点（见桥接表）。矿也是节点。
- **超边 = 反应**：`MolBalance.Reaction` 现在多带一个 `Set<Machine> machines`（不可变、非空）。
  超边是「{多个反应物} → {多个产物}」；不是节点到节点的普通有向边，所以**没有**用
  species×species 稠密矩阵 —— 矩阵表达不了「一条边牵动多个节点」，也没地方挂机器属性。
  图里存的是稀疏关联（每条边自己的反应物 / 产物列表），再派生 CSR 风格倒排行：
  `edgesAsReactant(speciesId)`、`edgesAsProduct(speciesId)`、`edgesFor(Machine)`（值都是边下标，
  与 `ReactionGraph.allEdges()` 对齐）。
- **机器属性**：`chemical/Machine.java` 七值 —— 化学三机 `REACTION_VESSEL / MIXER / ELECTROLYSIS_FURNACE`，
  选矿四机 `VEIN_EXTRACTOR / CRUSHER / CENTRIFUGE / MAGNETIC_SEPARATOR`。还原炉 / 置换炉做的是冶金，
  不是这些化学方程，所以不在枚举里（将来补焙烧档 RE 精矿 → RE2O3 时再加还原炉值）。
- 默认机器集按 `Kind` 派生，旧构造器一条都不用改：
  `THERMAL → {REACTION_VESSEL, MIXER}`、`STIRRING → {MIXER}`、`ELECTROLYSIS → {ELECTROLYSIS_FURNACE}`；
  另有显式机器集构造器（`Kind + Machine...`）给例外用。规范构造器拒绝空集，
  `MolRecipes` 另在类初始化时对整张表断言「每条反应至少一台机器」。

### 6.2 机器标注结果（34 条反应）
- `ELECTROLYSIS_FURNACE`：第 1 条氯碱、第 22 条水电解（`2H2O → 2H2 + O2`），共 2 条。
- `MIXER`（STIRRING，只有搅拌器）：第 2、3、15、17、21、29 条（HCl、SO3、NO2、NH3、HF、轻重稀土分家），共 6 条。
- `{REACTION_VESSEL, MIXER}`（THERMAL）：其余 26 条。
  原始日志可在启动时看 `[ReactionGraph]` 那一行；`edgesFor(Machine)` 可直接列出每台机器的边下标。

### 6.3 桥接表（矿 → 化学的接缝）
`ReactionGraph.buildBridge()` 是一张**很小、可手改**的表：只收录**机器已经存在**的步骤 ——
矿 → 精矿（抽取机 + 磁筛机 / 离心机 / 粉碎机），共 12 条：铁 3（磁铁矿 / 赤铁矿 / 褐铁矿 → 铁精矿）、

## 十、可逆反应与粗平衡（bug#20，2026-10-18）

用户口径：「简易一点就行，平衡常数太离谱的直接定位不可逆反应」——**不做真正的 K 标定**，粗模型 + 死区。

- `MolBalance.Reaction` 增 `reversible` + `equilibriumRatio`（产物总 mol / 反应物总 mol 的粗代理，默认 1.0）；
  旧 3/4/5 参构造器全部保留，默认不可逆 → 反应表其余各条行为逐 bit 不变。`Reaction.EQUILIBRIUM_BAND = 5%`。
- `Reactor` 对可逆反应每 tick 算 `Q = Σ产物mol / Σ反应物mol`：`Q < K` 正向、`Q > K` 逆向
  （`applyReverse` 消耗产物、生成反应物，复用 bug#19 同一套分数份 + 限速 + 产物容量机制），
  `|Q-K| ≤ 5%·K` 进死区不动；再夹一个「只推到平衡点、不越过 K」的上限，避免整份推进在平衡点两侧震荡。
- 标为可逆的 5 条：`N2+3H2<->2NH3`（K=0.25）、`CaCO3<->CaO+CO2`（K=6）、`MgCO3<->MgO+CO2`（K=6）、
  `2Al(OH)3<->Al2O3+3H2O`（K=6）、`2NaHCO3<->Na2CO3+H2O+CO2`（K=8）。产物被排出后 Q 下降，反应继续 —— 与机器的输出相逻辑天然配合。
- 其余维持单向：电解 / 燃烧式化合 / 置换 / HF 蚀刻 SiO2 / 接触法 `2SO2+O2→2SO3`（K≈10^24，一边倒）。
  `Cl2+H2O<->HCl+HClO` 因 `Chemical` 表里没有 HClO 物种而跳过（本任务不新增物种）。

  兑一批，一侧为空（`B/bFrac = 0`）或比率不整除时料就永久卡在缓冲里。算法抽到纯类
  `chemical/MolBlend.java`：先按比率兑「均衡段」，再把余料自由兑完，只受混合槽容量约束 ——
  容器内部是自由混合，比率是「精准配比」的偏好而不是闸门。反应釜的 `mix()` 本来就是自由兑入，未动；
  桶→缓冲路径本身不拒收气体/液体（`BucketMaterial.holds` 只查桶装不装得住自己的内容）。
- **反应缺边（Cause B）**：`Chemical` 表尾追加 `hypochlorous_acid`（HClO，M=52.5，LIQUID 溶液）；
  `MolRecipes` 追加可逆反应 `Cl2 + H2O <-> HCl + HClO`（STIRRING，只有搅拌器），粗平衡比 K=0.25
  （与合成氨同档）。质量守恒 71+18 = 36.5+52.5 = 89。`ChemicalTags` 抑制了公式误推的 OXIDE。
- 复算：15 Cl2 + 15 水 → 12 Cl2 + 12 H2O + 3 HCl + 3 HClO（Q=K 停住）；产物过量反向回推同一平衡；
  不搅拌不发生。2000 组随机料 / 9407 反应步，最大质量漂移 1.8e-12 g（浮点误差）。
- 语言：补齐 7 个精矿键（`chemical.geometallurgy.*_concentrate`）、`chemical.geometallurgy.halite`
  与 `chemical.geometallurgy.hypochlorous_acid`；中英各 636 键、键集一致、按 key 排序。

## 十二、反应速率 / 动力学（2026-10-18 用户口径）

用户报：「加一个反应需要时间吧，现在反应是瞬间进行的，这样有些次级反应可能无法进行」。
bug#19 给了分数推进，但机器上限仍是 RATE_PER_TICK = 1.0 **份/tick**（20 条方程/秒），
小批量 1~3 tick 就推完，多步链条里的中间体活不过一瞬间。本轮给每条反应标**耗时**。

### 12.1 模型（单位 / 默认 / 修正 / epsilon）

- **单位**：份/tick（一份 = 一整条方程）。速率是 MolBalance.Reaction 的新字段 rate，
  用 withRate(x) 标；MolBalance.Reaction 的旧 3/4/5/7 参构造器全部保留（默认走 DEFAULT_RATE），
  整数系数与类初始化质量守恒校验一字未动。
- **默认**：Reaction.DEFAULT_RATE = 0.25 —— 4 tick（0.2 s，20 tps）跑完一整条方程。
  只兜底将来新加、没显式标速率的反应；当前 44 条**全部显式标了**（见 12.2）。
- **有效推进**（Reactor.runAll）：
  min(限制试剂, ratePerTick × reaction.rate() × machineFactor × modifiers, 产物容量余量)。
  ratePerTick 是机器的吞吐**上限**（反应釜/搅拌器 1.0，电解炉溶液档 0.5），反应自己的速率按比例缩放它。
- **修正**（显式、乘性、可离线复算，Reactor.rateMultiplier）：
  - **催化剂在位 ×4**（CATALYST_RATE_BONUS）。催化剂仍是**存在性闸门**（缺了连一份都不跑，
    MolBalance.limiting 返回 0）；在位时再乘 4 提速 —— 两条语义叠加，不互相替代。
  - **搅拌中 ×1.25**（STIRRING_RATE_BONUS）。搅拌仍是闸门；需要搅拌的反应只有在搅拌时才跑得到这里，
    等价于常带这个加成。
  - **整机系数 machineFactor**（runAll 末参，AbstractReactorBlockEntity.machineRateFactor()）：
    反应釜 / 搅拌器 / 电解炉当前都传 **1.0** —— 机器层面的真实差异只有 ratePerTick 上限，留这个口备用。
  - **全表不变式**：rate × modifiers ≤ 1.0，所以吞吐上限始终压得住（贴上限的是 #2 HCl 合成 = 1.0）。
- **epsilon 兜底（选「抬高」不选「累加」）**：量化到千分位后若 < MIN_PROGRESS = 1e-3，
  **只有**「料够（exact ≥ 1e-3）+ 容量够（roomBound ≥ 1e-3）+ 且纯粹是速率太低」这一种情形
  会被 Reactor.slowFloorShouldLift 抬到 MIN_PROGRESS，保证极慢反应永远能前进。
  容量不够或料不够照旧跳过，不越界。**为什么抬而不累加**：Reactor 是无状态静态类，
  累加需要按「机器 × 反应」持久化进度（牵动存档格式与每机器一张进度表）；
  而 0.001 份/tick 已经是 1000 tick（50 s）一整条方程的「极慢」，真实玩法到不了，
  牺牲的只是「比这更慢」的表达力，换来一行兜底。

## 十三、标签驱动的规则生成（用户 2026-10-16 截图反馈）

现场：搅拌器状态「出料堵住」，混合槽 90 mol 满，内容为 氯气/水/氧化钠/盐酸/次氯酸。
用户结论：**复杂配方会卡死；应对性质明确的一类物质打标签（如「活泼金属氧化物」「能和水剧烈反应」），
用标签匹配现算配方，而不是写死**。**

### 13.1 先修的（堵料直接原因，纯行为/UX）
- 出料只推「该面角色里那一个相态」：一个面标成「出气」就永远推不走槽里 91% 的液体 → 槽满 → OUTPUT_FULL → 整机停住。
  1. 状态文本要说清**哪一相堵、堵了多少**；
  2. 未配出料相的面给**回退**：按槽内占比最大的相推，或明确报「此面推气相，槽内主要是液相」；
  3. 确认**满槽时不再从输入面吸料**（缓冲有上限，但满槽应完全停止。

**落地（2026-10-16 本轮，bug#23）：**
- 决策抽成纯类 `chemical/OutputRouting`（只碰 `MolStock` / `Chemical`，可在 JVM 里离线复算）：
  - `effectivePhase(stock, configured, MIN_MOL)`：面配的相在槽里有料（≥ `MIN_MOL`）时就按相出 ——
    玩家故意把液 / 气 / 渣分到不同面的路由照旧；配的相几乎为空（< `MIN_MOL`）时回退到槽里实际最多的一相，
    空白面因此不会把整机堵死。
  - `blocked(stock, MIN_MOL)`：给出「堵住的是哪一相、多少 mol」，就是状态栏那句话的数据来源。
- `AbstractReactorBlockEntity.pushFaces` 用 `effectivePhase`；`react()` 判 `OUTPUT_FULL` 时记下
  `blockedPhase` / `blockedMol`，经 `ContainerData` 的 `D_BLOCK_PHASE`（相序号 + 1）+ `D_BLOCK_MOL`
  （mol×100，钳 16 位）同步；菜单转发，`AbstractReactorScreen` 显示
  「出料堵住：液体 82.4 mol 推不出去」(`gui.geometallurgy.reactor_output_full`)。
- `pullFaces` 在槽余量 ≤ `MIN_MOL` 时直接返回：满槽时输入面不再从邻罐 / 桶吸料，输入缓冲也不再被喂
  （原先只看缓冲容量，槽满仍会继续灌缓冲 —— 这一条是真缺陷，已修）。
- 电解炉支路：`SmelterBlockEntity` 对溶液 / 阳极 / 阴极三本账做同一套计算，满账时报出堵住的相与 mol，
  经 `BLOCK_PHASE_INDEX` / `BLOCK_MOL_INDEX` 同步；`SmelterScreen` 在炉次进度条里显示
  「容器堵住：…」(`gui.geometallurgy.smelter_vessel_full`)。
- **未做**：13.2 / 13.3 的标签规则生成按计划留到后续轮次（本轮只动行为与 UX，不动化学）。

  Cs>Rb>K>Ba>Sr>Ca>Na>Li>Mg>RE>Al>Mn>Zn>Cr>Fe>Cd>Co>Ni>Sn>Pb>**(H)**>Cu>Hg>Ag>Pt>Au。
- **公式解析**（`parse` / `parseSpecies`）：括号、下标、`·` 水合物（含 `·10H2O` 组分系数）、
  多原子酸根整体识别（`SO4` 不会拆成 S+O4）、伪元素 `L`/`RE` 直接识别、`H`（重稀土）走显式别名表。
  输出 `Formula{atoms, units, unitCharges, charge, chargeResolved, solutions, problems}`。
  **要求每种元素只有一个氧化态使全式电荷归零**；无解或多解一律 `chargeResolved=false`，不猜。
- **查询**：`cationOf`（金属优先 → H⁺ → NH₄⁺）、`anionOf`（多原子酸根优先）、`chargeOf`、
  `valenceOf`/`valencesOf`、`isMetal`；结构判定 `isMetalOxide` / `isHydroxide` / `isCarbonate` /
  `isSulfate` / `isHalide` / `isSulfide`（前五个转发 `ChemicalTags`，不重复逻辑），另有策展的
  `isActiveMetalOxide`（碱金属 / 碱土金属氧化物）供 §13.2「活泼金属氧化物 + 水」规则用。
  未知 / 歧义返回 `null` / 空集，不抛异常。
- **显式表**：`FORMULA_ALIASES` 只重解释伪元素 H；`aliasOverriddenSpecies()` / `aliasesOf()` 可审计。

### 15.2 系数是解出来的（不允许按对写死）

对每个候选（反应物 id 列表 + 产物 id 列表）：取每种物质 `ChemicalData.parseSpecies` 的原子计数，
构造「元素 × 物种」齐次方程组，用 **BigInteger 精确有理数做 RREF**，求一维零空间，
通分 + 约分得最小整数系数。判为「配不平」并丢弃的情形：
自由变量为 0（无解）、自由变量 > 1（多解）、某系数为 0、两侧符号不一致、
或 `isMassBalanced` 质量校验不过。**绝不往表里放一条不平衡的反应，也绝不抛异常。**

### 16.3 氮源：空气（环境根 + 桥接边，不是 Chemical 物种）

- 空气是混合物，没有单一化学式，**不建 `Chemical` 物种**（否则必配出假式子）。按用户口径
  在 `ChemicalData.specialNodes()` 显式登记：`air / ambient-root / 一行理由`——可审计。
- `ReactionGraph.ORE_ROOTS` 加入 `air`（与 `water` 同为环境根），桥接表加一条**无玩家输入**的超边：
  `bridge:air-separation`：`air -> nitrogen + oxygen`，机器集 = **粉碎机（CRUSHER）**。
- **过程名取「空气分离」**而不是更宽的「气体分离」：这条边就是 air → N2 + O2 这一步单元操作，
  用具体名自解释；「气体分离」会预先占用将来其它气体分离步骤的名字。机器沿用任务指定的粉碎机。
- **实机可执行性（重要）**：桥接边只是**审计 / 科技线**建模，**目前进不了世界**。原因三条：
  1. 粉碎机的 `tick` 只有两条路——整件研磨（木炭 → 碳粉）与矿浆磨粉（浆进粉出），
     没有气体产物罐，也从不读 `MolRecipes`；
  2. `MolRecipes` 只由反应釜 / 搅拌器 / 电解炉里的 `Reactor` 执行，`Machine.defaultsFor` 永远
     不会把 CHEMICAL 反应派给 CRUSHER；
  3. `MolBalance.limiting` 对**零反应物**的反应返回 0（「没有反应物 —— 不成其为反应」），
     所以哪怕把它塞进反应表，反应循环也不会推动它。
- **玩家怎么开始？** 现状：开始不了——这是本轮明确的未落地项。要落地需要：
  (a) 宿主机器有能收 GAS 的输出/贮罐；(b) 一条「通电且产物有余量就自动跑」的环境进气行为；
  (c) `Reactor` 对零反应物的特殊分支（或另写一条不经过 limiting 的工艺通道）。
  这三项都属行为/界面改动，**本轮未做**；我只做了最小建模改动（环境根 + 桥接边），
  让审计与科技线先认这个节点。已在 §16.7 列为未验证项。

### 16.4 两个弱酸与规则 6

- `carbonic_acid` / `sulfurous_acid` 只登记物种，不写反应。规则 6 按「非金属氧化物原子计数 + H2O」
  在 `SPECIES_BY_ATOMS` 里现查，两条都命中并接受：
  `GEN CO2 + H2O -> H2CO3`、`GEN SO2 + H2O -> H2SO3`（均 STIRRING、可逆、K=0.25）。
- `SO3 + H2O -> H2SO4` 仍由硬编码表覆盖（`EXPLICIT_OVERRIDE`），速率/可逆未回改。
- 标签纠正（可审计，写在 `ChemicalTags.registerOverrides`）：
  - `carbonic_acid` 去掉 `CARBONATE`——它是酸本身，不是碳酸盐，否则规则 4 会拿它当碳酸盐置换，
    配出 HCl 两侧抵消的伪反应；
  - `sulfurous_acid` 去掉 `OXIDE`——公式含 O 被推导误标成氧化物；规则 6 靠原子计数匹配，
    不依赖这个标签。
- 解析器边界（诚实记录）：`H2SO3` 的亚硫酸根被读成单原子 `O²⁻`（`SO3` 基团会和中性 `SO3`
  冲突，没有建组）。因此 `ReactionRules` 新增 `saltFormingAnion`，把「酸根 = O²⁻」的酸从成盐规则
  里显式跳过，避免用「金属 | O」配出该金属自己的氧化物。亚硫酸盐（K2SO3 等）属未来建组后再谈。

## 十七、氮来自矿物 + 金属粉打通规则 5（本轮）

用户口径两条：
1. **空气分离不做**（低温精馏在这个技术层级荒谬）：删除 `air` 环境根与
   `air -> nitrogen + oxygen` 桥接边，氮改从**矿物**来。
2. **金属 + 酸 → H₂ 走金属锭粉碎**：金属锭在粉碎机里磨成**金属粉**，粉是 `Chemical` 物种，
   规则 5（金属 + 酸 → 盐 + H₂，活动性闸门）因此第一次真的生成。

### 17.1 删除空气分离
- `ReactionGraph.ORE_ROOTS` 去掉 `air`；桥接表删掉 `bridge:air-separation`，`ambient()` 辅助方法一并删除。
- `ChemicalData.specialNodes()` 清空 air 登记（机制保留，供将来真正「非单一化合物」的节点用）。
- `TechTree.stageOf` 去掉 `air` 分支。
- `nitrogen` / `oxygen` 不再依赖环境根：氧仍由 `2 H2O → 2 H2 + O2`（电解，水是根）供给，
  氮由下面的 `2 NH4NO3 → 2 N2 + O2 + 4 H2O` 供给。

### 17.2 氮族矿源（物种 + 矿物 + 脉石 + 桥接边）

### 17.5 为什么 `2 NaOH → Na2O + H2O` 与既有 `Na2O + H2O → 2 NaOH` 并存
两条单独看都是真的：常温 / 溶液里水合一边倒，高温焙烧时水蒸气离开、脱水才成立。
机器没有温度，所以两条都在表里 —— 密闭容器里会互相抵消（净零，不破坏守恒），
玩家要把水相从出口排掉才能把料推向 Na2O。这不是新引入的假反应。

## 十八、金属粉接线：`MetalPowderItem` 成为 `MolCarrier`（本轮）

§17.10 的「未接线」闭合：金属粉物品实现 `MolCarrier`，生存里把粉碎机磨出的粉放进机器
输入面的箱子（或拿在手上右键储罐），就能把金属单质喂进 mol 账，规则 5 的
`Zn + 2 HCl -> ZnCl2 + H2` 第一次真的可玩。

### 18.1 一件粉 = 0.1 mol（一锭 = 0.1 mol，与桶刻意不对称）
`MolStock.INGOT_MOL = 0.1`，`MolStock.BUCKET_MOL = 15.0` 保持不变（2026-10-16 用户口径，设计稿 §十五）。
粉碎机 1 锭 → 1 粉是 1:1 无损换算，所以一件粉 = **0.1 mol**。
桶是抽象的大量级载体，锭是 0.1 mol 的化学计量载体，所以 **1 桶 ≠ 150 锭是刻意的**。
因此「一锭的克数」不再物理对应真实锭重（Fe 0.1 mol ≈ 5.6 g，不是 837.8 g）——这是**有意接受的抽象**；
代价换来的是矿产量经济与反应数值一字不改。

### 18.2 内容现推，不存可变组件（bug#12 的教训）
`metal/PowderContent`（纯 Java，不碰 Minecraft 类型）把「金属键 → Chemical 金属单质 id → mol」
收成一条规则：铁族四个分级键（生铁 / 钢 / 合金钢 / 锻铁）还原成 `iron`；合金 / 稀土 /
非金属返回空账（粉进不了 mol 账）。`MetalPowderItem.stock` 每次现算，**不存任何 mol 组件**
—— 一摞粉因此没有「共享一个组件」的问题。

### 18.3 消耗路径
`MolCarrier` 新增 `consumedOnEmpty()`：默认 false（桶，倒空后同一只放回）；粉为 true。
`AbstractReactorBlockEntity.pullBucket` 见 true 时把计数减一（一件一次），
`BarrelBlock.useItemOn` 见 true 时从手里扣一件（整摞也安全，mirror `handOffOne` 的背包同步），
罐装不下整份就不动（阈值按载具自己的内容量算，不写死 15），避免倒掉的部分凭空消失。粉不可回灌（`room=0`、`add` 拒收）。机器 `pushBucket` 的灌装上上限也改成 `carrier.capacityMol()`，不再硬编码一桶 15 mol。

### 18.4 bug#26：机器路径漏了「一摞」守卫
顺带补上机器 `pullBucket` / `pushBucket` 对一摞内容桶的守卫（详见 bug 台账 bug#26）。

## 十九、矿石 → 金属链修正：精矿先磨矿粉、金属锭再磨金属粉（bug#27，本轮）

用户从科技线图上读到「铁精矿 --→ 铁粉」，指出真链是
**矿 → 精矿 →（粉碎机）矿粉 →（焙烧 / 浸出）化合物 →（还原炉 / 熔盐电解）金属锭 →（粉碎机）金属粉**。
核对代码后确认 `chemical/ReactionGraph.buildBridge()` 里 5 条「矿 / 精矿 --(CRUSHER)--> 金属物种」的边
同时犯两个错：（一）粉碎机只把料磨细、绝不会把矿变成金属；（二）`iron / manganese / aluminum / copper / zinc`
这些 mol 物种是**金属粉**（`item/MetalPowderItem` + `metal/PowderContent`），真正的来源是「金属锭 → 粉碎机」。

### 19.1 修正口径：只补机器已经存在的步骤

沿用 §6.3「桥接表只收录机器已经存在的步骤」的口径，把金属链补成五段，一段不多：

| 段 | 步骤 | 宿主机器 | 状态 |
|---|---|---|---|
| 1 | 矿 → 精矿 | 抽取机 / 磁筛机 / 离心机 / 粉碎机 | 已有（12 条），未动 |
| 2 | 精矿 → 矿粉 | 粉碎机（`CrusherBlockEntity`，只减粒度） | **本轮新增 7 条** |
| 3 | 矿粉 / 矿物 → 化合物 | 反应釜（焙烧）/ 离心机（浸出、结晶）/ 粉碎机（提纯） | 已有，仅把起点从精矿换成矿粉 |
| 4 | 化合物 / 矿 → 金属锭 | 还原炉 / 电解炉（`SmeltRoute` 的三条路线） | **本轮新增 6 条** |
| 5 | 金属锭 → 金属粉 | 粉碎机（`grindProduct`：锭 → 同成分粉） | **本轮改写 5 条** |

「金属锭」是本图新引入的非化学节点（此前图里没有锭节点），对应仓库里唯一的锭物品
`ModItems.INGOT`；金属锭在粉碎机里磨成粉，粉才是 `Chemical` 里的金属单质物种 —— 这是金属
进入 mol 世界的唯一入口，规则 5（金属 + 酸）靠它。

「真实世界 → 档位」的选档口径：
- **Spawn 看矿床频率**（不是元素丰度）：石英/硫/石墨等近地表常见成矿 → S1；
  斑岩铜、MVT 铅锌、红土镍 → S2；稀土副矿物、含银黝铜矿 → S3；
  锡钨、钴 → S4；钼、铋、金银、钻石 → S5。
- **Grade 看真实原位品位**：≥20% → G1，8~20% → G2，3~8% → G3，1~3% → G4，<1% → G5。
  **贵金属一档是刻意上调的**：真实岩金矿 1~5 g/t 在方块尺度上不可玩，这里把金/银/铋
  放到 G4（4.5%~7%）—— 矿看起来"富"得夸张，但它**稀有**（S5，只有 6% 的单元长），
  出现频率与丰度分开之后，稀有度由出现概率承担，不再靠把浓度压到 0。
- **Body 看该矿原本的采出量**：原本体积过大的（磁铁矿 DISC 26、赤铁矿 DISC 30、
  黄铜矿 DISSEM 30）收到 B1；原本太小的（金/银/铋 LODE 8~11、锡石/黑钨矿 LODE 12~13、

### 21.1 电解炉溶液档不再画「进 / 锭」两个页签（bug#35）

- 现场：截图里电解炉在溶液档（`溶液 15`、阳极 / 阴极容器条、`进料成分` 环），右侧页签列仍有

  而溶液档只有溶液 / 阳极 / 阴极三本账（矿粉罐与产物槽都只属于熔盐 batch）。
- 修法：页签位置与语义 id 拆开，新增 `tabIds()`：

  `solutionMode()` 门控）。真物品槽的增删不能按 `solutionMode()` 做 —— 客户端构造菜单时
  `ContainerData` 还是全 0，会与服务端数出不同的槽数。

### 21.2 焙烧类分解移出常温反应釜：新增 `Kind.ROASTING`（bug#36）

## 二十六、桶装 CO / H₂ 当还原剂（气体还原剂入还原炉，2026-10-20）

用户口径：「CO/H₂ 气体还原剂载体：桶」—— 装着 CO 或 H₂ 的药剂桶必须能在还原炉里当**还原剂**用，
和现有碳系并列。本轮只动还原炉的试剂准入 / 消耗路径，**不改功率常量、不改存档格式、不改化学表顺序**。

### 26.1 准入：还原路认三类，活动性闸门仍只属置换炉

`SmelterProfile.ReagentKind.accepts` 仍是**唯一**准入点，`REDUCTANT` 现在认：

1. 碳系（`Reagent.isCarbonFamily`，煤炭 / 木炭 / 碳粉 / 碳棒）—— 主路，恒可；
2. 能读出金属 id 的锭（可选替代，这是既有行为）；
3. **桶装 CO / H₂**（`Reagent.isGasReductant`）—— 载体必须是 `MolCarrier`，
   且桶里**每一种**成分都是还原性气体（混装水 / 酸的桶整桶作废，返回 0 当量）。

`reagentFits` 只对**置换炉**做活动性判定（未改）；还原炉不按活动性卡人。
置换炉 `metalOf != null`、电解炉 `isElectrode` 都不认气体桶。

### 26.2 当量：1.0 当量 = 夺走 1 mol 氧

新纯类 `chemical/ReductantGas` 是气体当量的唯一来源（无 `net.minecraft` 依赖，可离线复算）：

| 气体 id | 反应 | 每 mol 夺氧 | 当量 / mol |
|---|---|---|---|
| `carbon_monoxide` | CO + [O] → CO₂ | 1 mol | **1.0** |
| `hydrogen` | H₂ + [O] → H₂O | 1 mol | **1.0** |

刻度与碳系一致：`Reagent.CARBON` 里碳粉 = 1.0，本征化就是「一件碳粉 = 1 mol C」
（C + [O] → CO，每 mol 碳夺 1 mol 氧）；煤炭 0.8、木炭 0.9、碳棒 1.5 是每件含碳的摩尔数。
两种气体化学计量相同（都 1.0），仍分列常数以便日后单独调价。一个满桶 15 mol ⇒ **15.0 当量**。
`units(MolStock)` 遇任一非还原性成分即返回 0（整桶作废）。

### 26.3 消耗：抽气体、不抽桶

`SmelterBlockEntity.payReagent` 分两条补法：

- **普通试剂**（碳系 / 金属）—— 取走整件、按件计当量（既有路径，未改）；
- **气体桶** —— `drawGas` → `drawGasInto(bucket, wantUnits)`：先用 `ReductantGas.draw`
  从账上扣出最多 `wantUnits` 当量的气体（负数=扣减走 `MolStock.take`，bug#9 口径），
  再按扣出来的账对**同一只桶**调 `MolCarrier.take`（与反应釜 `pullBucket` 同一条 MolCarrier 路径），
  最后把抽完的桶写回试剂槽。抽干只剩空桶时，`MolCarrier.take` 清掉内容组件，**同一件桶物品原地留下**，
  `items.setChanged()` 由菜单下一次广播同步给客户端。**桶本身不消耗。**

`canPayReagent` 对气体桶按 `Reagent.gasUnits(stack) >= units` 判够不够（mol 现推，不是「一件 = 固定当量」）。

### 26.4 「一次一件」守卫（bug#12 / bug#26 同类）

一摞桶共享同一个 `bucket_stock` 组件：整摞抽气会「抽了 16 只、只记一份账」。新增
`Reagent.oneAtATime(stack)`：非消耗品载具（桶）只允许单只，消耗品（金属粉 `consumedOnEmpty`）与
普通物品不受限。守卫同时收在 `SmelterBlockEntity.acceptsReagent`（服务端 + 漏斗面）与
`SmelterMenu.placeholder.canPlaceItem`（客户端空壳）两处，**客户端不读机器状态**，
所以不会重现 bug#35 的槽位错位；本轮**没有新增 / 删除任何 `addSlot`**。

## 二十七、虚拟日历 + 探测仪纪元基准修复（bug#45，2026-10-18 实机反馈）

### 27.1 现场

用户实机（赤铁矿）：探测仪报出「最近的赤铁矿矿脉中心」和坐标，按坐标去挖 / 摆机器，矿脉中心却**没有任何矿物**。
用户追问「矿脉会流动吗？如果会，可以加一个虚拟日历用来计算流动」。

### 27.2 纪元到底是什么（读代码，不是读文档）

三个常量定死在 `vein/EpochClock`：`TICKS_PER_DAY = 24000`、`DAYS_PER_EPOCH = 10`、
`TICKS_PER_EPOCH = 240000` 刻（≈ 现实 3.3 小时，只在有玩家在线时推进）。

纪元号有两种算法：

| 基准 | 代码 | 用途 |
|---|---|---|
| 全局纪元 | `EpochClock.globalEpoch(level) = floorDiv(gameTime, 240000)` | 只是「世界日历」 |
| 单元纪元 | `EpochClock.epoch(gameTime, chunkX, chunkZ) = floorDiv(gameTime + offset(chunkX, chunkZ), 240000)` | 每个区块带一个 0~240000 的确定性偏移，换脉时刻互相错开 |

`OreBody` 是 `(世界种子, 矿体单元坐标, epoch)` 的纯函数：epoch 进 `cellSeed` 的哈希，也进
`GeologySampler.rockAt`。**epoch 差 1，整个矿体的矿物组合、形状、中心全都不一样。**

### 27.3 根因：两个消费者用了两种纪元基准

- 探测仪 `prospect/Prospector` 用**单元纪元**（单元起始区块，`(cellX*32)>>4 = cellX*2`）；
- 挖掘机 `FluidVeinExtractorBlockEntity` 与纯函数入口 `VeinDeposit.at(level,pos)` 用**全局纪元**。

两者约三成的情况下相差 1 个纪元，于是探测仪报的是纪元 N 的矿体中心，机器在同一个坐标
按纪元 N-1 重新生成，得到的是一块**纯原岩**（或另一种矿体）。

一次性 plain-Java harness（已删）实测，种子 `20261018`、玩家 `(0,64,0)`、`gameTime=228000`
（世界第 0 纪元、该单元第 1 纪元）：

| 量 | 探测仪报告的 | 机器（旧，globalEpoch） | 机器（新，单元纪元） |
|---|---|---|---|
| 中心 | (16.85, 54.33, -15.12) | (16,54,-16) | (16,54,-16) |
| 母岩 | andesite | — | — |
| 该点矿物 | peak 35.6% | **[]（一种矿物都没有）** | [hematite=0.4025, chalcopyrite=0.0162, fluorite=0.0711] |

同一 harness 在玩家周围扫了 9267 次赤铁矿读数：`reading.epoch` 与单元纪元 100% 一致；
**旧基准下 27.1% 的报告中心是空的**，新基准下 **0%**。

> 补充：单元是 32 格，横跨两个区块，而偏移是按 16 格区块算的。若把机器的纪元改成
> 「方块自己所在区块」，同一个单元的两半会得到两个纪元、两个矿体。所以基准必须落在
> **矿体单元**（单元起始区块）上，为此新增 `EpochClock.epochOfCell(...)`。

### 27.4 修法

| 文件 | 改动 |
|---|---|
| `vein/EpochClock.java` | 新增 `epochOfCell(...)` / `ticksUntilNextCell(...)` / 私有 `cellChunk(...)`；单元纪元固定取单元起始区块 |

### 28.2 附录表列被裁切（bug#47）

根因两条，都在 `client/ManualPager`：

1. **列宽总和可能超过纸宽** —— 每列都被抬到至少 12 px、最后一列「吃掉剩余」，权重和大于页宽时
   总和溢出，多出来的列整块落到纸外；

   `H₂O` 变 `H2`。
